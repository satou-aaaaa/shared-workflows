# 天秤の書の週1の Lighthouse で、速さが 36 点（下限 53 点）に落ちた

- 種類: 検査の見逃し
- 場所: tenbin（天秤の書）の Lighthouse（共通部品 lighthouse.yml）
- 気づいた人: CI（週1の Lighthouse）と監督の巡回
- 影響: 初めて開いた人のスマホで、ホームが描かれたあとに「どの試験の勉強をしますか？」の枠が上に入り、下の中身が約 380px 押し下げられていた（CLS 0.357）。最初の画面までも約 10 秒（11/2 は約 5.5 秒）。tenbin #122 が開いた。

## 起きたこと
- 2026-11-09 10:08 JST、週1の Lighthouse で performance が 36 点になり落ちた（11/2 は通過）。
- 手元で同じ条件で測ると、11/2 の版は 66 点、11/9 の main は 36 点。CLS が 0.005 → 0.357、LCP が 5.5 秒 → 10.5 秒。
- 11/2〜11/7 に index.html が 2.8MB → 7.2MB（圧縮して 0.65MB → 1.67MB）になり、11/7 に初めての人への質問の枠（tenbin #119）が入っていた。

## 原因
- ホームを整える小さな処理（本体の前に置いた第5〜11回の処理）が DOMContentLoaded を待って見張りを始めていた。本体はその後ろの1つの大きな script でホームを描くので、ホームが一度描かれ、残りの数 MB を読み終えてから枠が上に足された。
- 本体が大きくなるほど、描いてから枠が入るまでの間が長くなり、ずれとして数えられた。
- 重さは、条文の本文（GY_JOBUN と、ほかの資格試験の条文で約 2.9MB）など、最初の画面に要らないデータを本体に入れ続けたため。

## なぜ見つからなかったか
- PR ごとの Check（`tools/check.mjs`）は、画面が開けるか・中身が正しいかを見ていたが、描いたあとのずれ（CLS）と送る量は見ていなかった。
- 速さを測るのは週1の Lighthouse だけで、1週間に入った十数本の PR のどれで落ちたかは、その場では分からなかった。

## 対策
- [x] 直す: 6つの処理の見張りを、`#app` ができた時点で始めるようにした。手元の Lighthouse で 36 → 56 点、CLS 0.357 → 0.006（tenbin #123）
- [x] 防ぐ: `tools/check.mjs` に、初めて開いた画面の CLS が 0.1 を超えたら落とす検査を足した。直す前の main では「スマホ CLS 0.336」で落ちることを確かめた（tenbin #123）
- [x] 見つける: `tools/check.mjs` に、index.html の送る量（圧縮して 2MB まで）の上限を足した。次に大きく重くなる PR は、週1を待たずにその PR で落ちる（tenbin #123）
- [ ] 弱める: 条文の本文など最初の画面に要らないデータを別のファイルにして後から読み、最初の画面を 11/2 の速さ（約 5.5 秒）に戻す。今の 56 点は下限 53 点に近い（担当: 天秤の書の読み込みを速くするスレッド、期限: 2026-11-16）
