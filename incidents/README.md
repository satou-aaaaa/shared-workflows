# incidents/ — 起きた問題の記録（再発防止）

satou-aaaaa の全プロジェクトで起きた問題を1件1ファイルで残す場所。直して終わりにせず、同じ種類の問題が二度と起きない仕組みを入れたかを、あとから誰でも確かめられるようにする。
（2026-10-19 satou さん「一度何らかの問題が発生した時、仕組みを改善することによって、同様の問題が二度と起こらないようにしてください」「管理しているプロジェクトでも、同様にしてほしいです」）

決まりの正は [routines/common.md](../routines/common.md)「問題が起きたら（再発防止）」。直すときの手順はスキル `saihatsu-boushi`（控えは [bootstrap/skills/](../bootstrap/skills/saihatsu-boushi/SKILL.md)）。

## 記録するもの

- 遊ぶ人・satou さんに見える不具合（表示崩れ・ボタンが効かない・公開ページが壊れた）
- 検査・レビュー・見回りが見逃したもの（あとから satou さんや別の担当が気づいた）
- 連絡の行き違い（届かなかった・重なって届いた・同じ依頼を satou さんが2回した）
- 手順の失敗（ルーティンが止まった・確認待ちで進まなかった・決まりと違うことをした）

1行で直せて、だれにも見えず、検査がその場で見つけたもの（push 前の確認で落ちた等）は書かなくてよい。

## 書き方

- ファイル名は `YYYY-MM-DD-<英小文字とハイフンの短い名前>.md`（日付は起きた日か気づいた日）。
- 同じ PR で、下の「一覧」に1行足す。
- 個人情報（転職先・お金・顧客の名前など）が絡む件は、公開リポジトリであるここには書かず、非公開の satou-aaaaa/ops-backup の `incidents/` に同じ形で書く（一覧にも載せない）。
- 人や AI を責める書き方をしない。「注意する」「気をつける」「確認を徹底する」は対策にならない。仕組みのどこに穴があったかを書く。
- 内部の ID（メッセージ・セッション・ルーティンの ID）やメールアドレスは書かない（Lint が落とす）。スレッドは名前で書く。

Lint（`scripts/check-incidents.mjs`）が、見出し・種類・対策の形・一覧への載せ忘れを毎回調べる。

```markdown
# <何が起きたか1行>

- 種類: <下の「種類」から1つ>
- 場所: <リポジトリ・アプリ・ルーティン・スレッドの名前>
- 気づいた人: <satou さん／監督の巡回／CI など>
- 影響: <誰に何が起きたか。数字があれば数字で>

## 起きたこと
<事実だけを時刻順に。2〜5行>

## 原因
<なぜ起きたか。仕組みのどこに穴があったか>

## なぜ見つからなかったか
<検査・レビュー・見回り・手順のどれが、なぜ見逃したか>

## 対策
- [x] 直す: <起きた問題そのものを直したこと>（PR・版）
- [x] 防ぐ: <同じ種類が起きなくする仕組み>（PR・版）
- [ ] 見つける: <起きてもすぐ気づく仕組み>（担当: <スレッドかルーティンの名前>、期限: YYYY-MM-DD）
```

- 同じ直しをほかのリポジトリへ広げるときは、ファイル名でなく中身（同じコマンド・同じ書き方）で全リポジトリを探す。`scripts/drift-check.mjs` に決まりを足したら、その PR で全リポジトリに回し（`GH_TOKEN=… node scripts/drift-check.mjs`）、今ある違反を週次まとめを待たずに同じ日に直す（2026-11-07-tenbin-check-timeout.md）。
- 対策の行は `- [x]` か `- [ ]` で始め、`直す:`・`防ぐ:`・`見つける:`・`弱める:` のどれかを付ける（Google SRE の action item の種類）。
- `防ぐ:` か `見つける:` が1つも無い記録は Lint が落とす（直しただけで終わらせないため）。
- 済んだ `防ぐ:`・`見つける:` には、あとから確かめられる証拠を1つ書く。PR・Issue の番号（`#12`）、版（`v31`・`18版`）、`` `ファイル` ``、`[名前](リンク)`、「この PR」、手順の番号（`手順10`）のどれか。無いと Lint が落とす（書いただけの対策を防ぐ）。
- まだ済んでいない `- [ ]` には「担当」と「期限」を書く。期限を過ぎたもの・14日以上残ったものは、週次まとめの「次にやること」に出る（`scripts/next-actions.mjs`）。

## 種類

繰り返しを数えるための分け方。足すときはこの表に1行足す（Lint はこの表にある名前だけを通す）。

| 種類 | 例 |
| --- | --- |
| 操作の反応 | 押しても見た目が変わらない、二度押しできる、結果が出ない |
| 表示 | 崩れ・読めない・はみ出す |
| 動作 | 計算や判定の誤り、エラーで止まる |
| 見回りの見落とし | 監督・見回り・巡回が、止まったものや返事待ちを拾わなかった |
| 連絡の行き違い | 届かない・重なって届く・届け先の間違い |
| 検査の見逃し | CI・QA・レビューが通したのに壊れていた |
| 手順の抜け | 手順書に無い・古い・決まりと食い違う |
| 公開・CI | 公開が壊れた、CI の部品が止まった |
| 権限・設定 | 許可待ちで止まった、設定の漏れ |

## 繰り返していないかの点検

- **毎週（CI、Claude は使わない）**: 月曜の「週次まとめ」Issue の「次にやること」に、残っている対策と、30日のうちに同じ種類が2件以上あった種類が出る（`scripts/next-actions.mjs`）。
- **毎週土曜（Claude）**: ルーティンとスキルの定期見直し（[routine-review.md](../routines/routine-review.md) の D）が、この1週間の記録と上の出力を読む。同じ種類が繰り返していれば、一つ一つの対策が効いていないので、もっと根本の仕組み（共通の検査・部品・手順書の作り直し）を入れる。
