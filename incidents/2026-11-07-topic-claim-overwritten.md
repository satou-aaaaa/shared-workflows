# 同じ題材「祝日の由来」を、2つのスレッドが並行で作った

- 種類: 手順の抜け
- 場所: プロジェクトのメモリ game-queue（題材の担当の書き場所）・routines/game-dev.md 手順A の1・shared-workflows の Create repo
- 気づいた人: コーディネーター
- 影響: 2026-11-07 に1回。スレッド「百人一首あわせ」が shukujitsu-yurai（祝日の由来）を作って PR #1 まで出したあと、伝統工芸品のスレッドが先に同じ題材（shukujitsu「祝日のいわれ」）の担当を書いていたと分かった。片方を止めたので公開は1本だけ。止めた側の作業がむだになった。題材の重なりは同じ日に3回目（防災の判断・リサイクルマークよみ・祝日の由来）。遊ぶ人への影響は無い。

## 起きたこと
- 「百人一首あわせ」は game-queue を `grep 祝日` で見て、担当が無いのを確かめてから、末尾に「祝日の由来 → shukujitsu-yurai … 担当」の1行を足し、Create repo を起こした。
- ほぼ同じ時に伝統工芸品のスレッドも game-queue を書き直し、「祝日の由来 → shukujitsu「祝日のいわれ」… 担当」を足した。あとで見ると、game-queue に残っていたのはそちらの行だけで、「百人一首あわせ」の行は消えていた。
- Create repo は名前（shukujitsu-yurai と shukujitsu）がちがうので止めなかった。似た名前の検査は長音とハイフンをそろえるだけで、語の後ろが足された名前は別物と見る。

## 原因
- 担当の正が、プロジェクトのメモリのファイル1つ（game-queue）だった。メモリはファイルごと書き直す形で、後から書いたほうが勝つ。2つのスレッドが同じころ書くと、先の行が消える。「書いてから作る」を守っても防げない。
- Create repo は、題材の担当を見ていなかった（見られる所に担当が無かった。メモリは GitHub の Actions から読めない）。

## なぜ見つからなかったか
- これまでの対策（incidents/2026-11-07-same-game-different-romaji.md）は、公開済みの表を日本語で探すことと、似た名前のリポジトリを止めることで、「作っている途中」の担当どうしの重なりは見ていなかった。

## 対策
- [x] 直す: 祝日の由来は shukujitsu-yurai（PR #1）を残し、もう一方はコーディネーターが止めた。担当の Issue「題材: 祝日の由来（祝日）」を立てた
- [x] 防ぐ: 担当の正を shared-workflows の Issue「題材: 〇〇（題材の言葉）」にした。Issue の番号は先に立てたほうが小さく、消えたり書きかえられたりしないので、いちばん小さい番号を担当とする（routines/game-dev.md 手順A の1、この PR）
- [x] 防ぐ: Create repo に `claim`（担当の Issue 番号）と `topic`（題材の言葉）を足し、同じ言葉の「題材:」Issue に小さい番号があるとき・公開済みのゲームの表にその言葉があるときは作らずに止める（.github/workflows/create-repo.yml、この PR）
