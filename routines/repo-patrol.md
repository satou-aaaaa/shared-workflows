# 全リポジトリ・全プロジェクト巡回と改善提案（毎日 22:38 JST）

先に `common.md` を読むこと。追加のルーティンは作らず、この1本で行う。負荷は抑えめに。
（satou さんの依頼 2026-10-14「所有リポジトリをすべて巡回し改善提案、提案はそこを専門とする agent に渡す」「毎日行う」「各プロジェクトの改善提案等も定期的に行う」、2026-10-15「新しいプロジェクトも管理したい」）

**早めに終える**: 最初に、前回の巡回以降に動きがあったリポジトリ・プロジェクトだけを洗い出す（list_repos の pushed_at、新しいコミット・PR・Issue、ルーティンの last_run の変化）。動きが無いものは読まずに飛ばす。全部動きが無く、新規の対象（手順A）も無ければ update_status を1行更新するだけで終える。

0. **節約モード**なら今回は巡回せず update_status だけ更新して no_reply_needed で終える（手順Aの新規検出と記録だけは行ってよい）。list_triggers は1回読んだ結果（id・名前・persistent_session_id・hearth_channel_id・last_run）を以降の手順で使い回す。
A. **新しい対象の自動検出**（毎回。軽い比較だけ）: チームメモリ repo-patrol の「既知リポジトリ」「既知プロジェクト」と、list_repos の結果・手順0の一覧の hearth_channel_id を突き合わせる。メモリに無いものが新規。新規が見つかったら
   (1) 新リポジトリは add_repo（owner と repo を別々に渡す）して読み取り用に加え、
   (2) repo-patrol の既知一覧に追記し、
   (3) 監督スレッドの担当セッション（「監督エージェントの巡回」trigger の persistent_session_id）に send_message で「新しいリポジトリ／プロジェクト <名前・chan/リポジトリ・担当セッション> を巡回対象に加えた。監督の点検対象にも加えてほしい」と1回だけ伝え、
   (4) 今回の巡回で初回の読み取りを行い、reply の先頭に「新規対象：…」と1行書く。
   新しいリポジトリが satou-aaaaa のもの（フォークでない）で、CI の共通部品（shared-workflows の `template/`）や main の保護が入っていなければ、提案で止めず、
   このプロジェクトのコーディネーター（mcp__hearthbot__get_channel_session_id）に send_message で「<リポジトリ> の受け入れスレッドを始めてほしい：shared-workflows の `routines/onboarding.md` の手順どおりに」と1回だけ頼む（2026-10-16 satou さん承認。手順は 2026-10-18 に onboarding.md へまとめた）。他の人のリポジトリには何もしない。
   個人情報中心のプロジェクト（転職など）は中身を読まず、ルーティンの失敗・滞留・重複・CI で済む作業という運用面だけを見る。
1. 動きのあるリポジトリだけ git clone --depth 1（既にあれば pull）。チームメモリ repo-patrol を読み、前回までの提案と渡し先を確認する。
2. 動きのあったリポジトリだけを巡回する。前回渡した提案がまだ手つかず（Issue が開いたまま動きが無い、担当から反応が無い）のリポジトリには新しい提案を足さない。各リポジトリで、オープン／最近クローズの Issue・PR と重複しない、根拠（file:line・実行結果）のある改善提案を最大3件にまとめる。読み取りのみ。コードの変更・PR作成・マージはしない（担当エージェントの仕事）。
   渡す改善案のうち取り消せて、お金がかからず、satou さんの方針と食い違わない改善案は、担当に「satou さんの確認は要らない。導入まで進めて結果だけ報告」と書いて渡す（2026-10-16 satou さん。autonomy.md）。
3. **渡し方**（担当は手順0で読んだ一覧で確かめ、変わっていればメモリを更新）:
   - last-tell: LAST TELL（ポーカーアプリ）プロジェクトの「毎日の改善提案」担当セッション（その trigger の persistent_session_id）に send_message。
   - carcassonne-research: カルカソンヌ プロジェクトの担当セッション（チームメモリ repo-patrol に記載。自己対戦は 2026-10-14 に CI の selfplay.yml へ移り、元のルーティンは無効なので有効な一覧には出ない）に send_message。
   - sandbox: 週1の新規Issue提案係が担当するので巡回しない。
   - dungeon-boardgame: Issue を起票すれば「ダンジョンボドゲ issue 自動対応（3時間ごと）」の担当が拾う（追加の連絡は不要）。
   - tenbin: Issue を起票したあと、このプロジェクトのコーディネーター（mcp__hearthbot__get_channel_session_id で取得）に send_message で「tenbin Issue #N の修正スレッドを始めてほしい（修正PR・CI・マージまで。法律の内容に関わる判断は推奨案を添えて satou さんに確認）」と頼む。1回の巡回で頼むのは最大1件、前に頼んだ件のPRがまだ開いているあいだは次を頼まない。
   - naitei-no-michi（転職ノベルゲーム「内定への道」、プロジェクト「転職ゲーム」。2026-10-18 追加）: 専任のルーティンは無い。tenbin と同じく Issue を起票し、コーディネーターに修正スレッドの開始を頼む（1回の巡回で最大1件、前に頼んだ件の PR が開いているあいだは頼まない）。
   - tenbin（別枠・毎週日曜 JST の巡回で1回だけ）: 「論文問題を1問追加（add-ronbun-questions スキルで）」の Issue を起票し、コーディネーターに修正スレッドの開始を頼む。前週の問題追加 PR が開いていれば足さない。その PR は作った担当ではマージせず、次の手順の「2人目の確認」に回す旨を依頼に書く。
   - **tenbin の2人目の確認**（毎回。2026-10-16 satou さん承認。autonomy.md の「確かめてから任せること」）: tenbin の開いた PR のうち、問題・判例・条文に触れるもの（data や問題ファイルを変えるもの）で、CI が緑、まだラベル「確認済み」も「satou確認」も付いていないものを1回に最大2本読む。
     確かめるときは、PR の模範答案や説明文を読む前に、判例の事件番号・年月日から一次資料を開き、判旨の該当部分を先に書き写す（書き手の文章に引きずられないため。LLM は自分と同じモデルの出力をひいきしやすい）。PR に判例ごとの裁判所のページの URL と判旨の引用が無ければ、それだけで「satou確認」にする。引用は一次資料のページにそのままあるかを文字で照らす。CodeRabbit のレビューに判例の指摘があれば、それも1件ずつ確かめる。
     作った担当とは別の目で、PR に出てくる判例（裁判所・年月日・事件番号・判旨）と条文を一次資料（裁判所の判例検索 https://www.courts.go.jp/app/hanrei_jp/search1 、e-Gov 法令検索 https://laws.e-gov.go.jp/ ）と1件ずつ突き合わせ、模範答案・規範カードが判旨と食い違っていないかを見る。
     全部確かめられて問題が無ければ、確かめた出典の一覧を PR にコメントしてラベル「確認済み」を付け、ask_decision のカード（「satouさんにお願い：tenbin #N を公開してよいか」、PR へのリンクと確かめた出典の数、選択肢は「マージする」「直させる」「取り下げ」）で聞く。「マージする」なら squash マージする（tenbin の Changes が更新情報を作る）。法律の誤りは学習者に害があり、AI どうしの確認だけでは見落としが残るため、マージの前に satou さんの目を通す（2026-10-18）。
     食い違い・確かめられない点（一次資料が開けない場合を含む）があれば、その点を PR にコメントし、ラベル「satou確認」を付けて、ask_decision のカード（「satouさんにお願い：」、選択肢は「直させる」「このままマージ」「取り下げ」）で聞く。直させるなら tenbin の修正スレッドにコメントの内容を伝える。
   - shared-workflows: 共通部品。巡回では、各リポジトリの呼び出し側と食い違いが無いかだけ見る（直すときはこのリポジトリへの PR を担当に頼まず、提案として reply に1行）。
   - kotlin-csv は他の人のもの。巡回・提案・設定変更を一切しない（satou さん 2026-10-16）。
4. **プロジェクトの巡回**（リポジトリでは見えない運用面）: 手順0で読んだ一覧の hearth_channel_id で satou さんのプロジェクトを洗い出す（このプロジェクト（監督・巡回が動くプロジェクト）は除く。ルーティンの見直しは別スレッドが週1で担当）。各プロジェクトの担当セッションを get_session で読み、前回の巡回以降に動きがあったプロジェクトだけを見る。見るのは、ルーティンの last_run の失敗、post_turn_summary の needs_action や長く止まった need_input、同じ作業の重複、成果物の滞留など、根拠を示せるものだけ。提案はプロジェクトごとに最大2件。渡し先はそのプロジェクトの担当セッションに send_message（アーカイブ済みなら parent_session_id を試す。どちらも無理ならメモリに記録して報告に書く）。監督エージェントの点検（止まっているものの再開）と同じ件は渡さない。
   リポジトリでもプロジェクトでも、Claude を使わずに CI で済む定型作業が Claude のルーティンに残っていないかも提案の観点に入れる。
5. 提案を渡したとき、または新規対象を加えたときだけ、このスレッドに reply で、リポジトリ／プロジェクトごとに1行（提案件数・渡し先・リンク）。satou さんの判断が要るものは、選べる形なら ask_decision のカード（`common.md` の「satou さんへの連絡」）で出し、カードで答えられないものだけ「satouさんにお願い：」を付けて先頭に置く。提案も新規も0件なら update_status だけ更新して no_reply_needed。メモリ repo-patrol を更新する。
